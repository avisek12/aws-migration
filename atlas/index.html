How the two live together

This atlas is the map — decisions, sequence, and the shape of each strategy. The docs/ folder is the terrain — full step-by-step runbooks, templates, and worked examples for every section here. Where a section below is a summary, it links to its source doc for the complete version.

Two frameworks run through everything that follows: the 6/7 R's decide what happens to each application, and the migration factory operating model decides how a wave of applications actually moves, repeatably, without every server being a bespoke project.

02 · Disposition

The 7 dispositions

Every application gets exactly one of these before it enters a wave plan. The mix you land on drives timeline, risk, and cost more than any other decision in the program.

01 · RETIRE

Retire

Decommission apps with no ongoing business value — redundant, unowned, or already superseded.

Application Discovery Service
02 · RETAIN

Retain

Leave it where it is — compliance lock-in, recent investment, or simply not prioritized yet.

Revisit trigger logged
03 · RELOCATE

Relocate

Move VMware workloads at the hypervisor level, unchanged — fastest path for a VMware-heavy estate.

VMware Cloud on AWS + HCX
04 · REHOST

Rehost

Lift-and-shift onto EC2 with no code change. Time-boxed, low-risk, defers modernization.

AWS MGN
05 · REPLATFORM

Replatform

Lift-tinker-shift — swap a self-managed component for a managed AWS service, same architecture.

DMS + SCT, App2Container
06 · REPURCHASE

Repurchase

Replace a licensed or homegrown app with a SaaS equivalent.

AppFlow, Identity Center
07 · REFACTOR

Refactor

Redesign for cloud-native — containers, serverless, managed data services — for apps that justify it.

ECS / EKS / Lambda
Rule of thumb

A healthy wave-1 portfolio skews 60–70% Rehost/Replatform, 10–20% Retire/Retain, and the remainder Refactor scheduled for later waves once the landing zone and the factory team are proven. Full decision tree and workshop template: docs/02-6r-migration-strategies.md.

03 · Method

Migration methodology

Four phases, the first two run once, the third repeats per wave, the fourth runs forever. Durations are typical for a 50–200 server estate — scale to your own.

00

Assess

Typical duration: 4–8 weeks

Activities

  • Server/app discovery, agentless or agent-based
  • Dependency mapping to group apps into waves
  • 7 R's classification per application
  • TCO / business case via Migration Evaluator

Exit criteria

  • Signed inventory and disposition per app
  • Approved business case
  • Initial wave groupings
01

Mobilize

Typical duration: 4–10 weeks

Activities

  • Landing zone build (accounts, network, guardrails)
  • Migration factory tooling stood up: MGN, DMS, Migration Hub
  • Wave planning against dependency graph + business calendar
  • Pilot migration — 1–2 low-risk apps

Exit criteria

  • Landing zone passes security review
  • Pilot wave migrated and validated
  • Factory runbooks proven
02

Migrate & modernize

Rolling, per wave — 2–4 weeks each

Activities

  • Replicate, test-launch, cut over per app (see §08)
  • Post-cutover bake, sign-off, decommission source
  • Modernize where the disposition calls for it

Exit criteria

  • All apps in the wave signed off
  • No open P1/P2 incidents
  • Source decommissioned or scheduled
03

Operate & optimize

Continuous, post go-live

Activities

  • Rightsizing via Compute Optimizer, then Savings Plans
  • Well-Architected review per workload
  • Ongoing FinOps and SecOps

Exit criteria

  • Handed to BAU ops with runbooks + on-call
  • Optimization backlog feeding future waves

Full phase detail, wave-planning principles, and the RAID log approach: docs/03-migration-methodology.md.

06 · LLD

Strategy playbooks — low-level design

Open each strategy for its step-by-step execution. These are the condensed runbooks; full versions with rollback plans and checklists live in docs/06 through docs/10.

Rehost — lift & shift via AWS MGN docs/06

Continuous block-level replication into EC2 with no code change — the fastest, lowest-risk exit from a source environment.

  1. Install the MGN replication agent — initial sync, then continuous CDC while the source stays live.
  2. Configure launch settings: instance type, subnet, security groups, IAM role, encryption.
  3. Monitor replication lag until stable for 24h+.
  4. Test-launch in an isolated staging subnet; run functional and performance validation.
  5. Cut over: freeze source, final sync, launch, re-point DNS/LB, smoke test.
  6. Bake 48–72h with source powered on as the rollback path, then decommission.
Replatform — DMS/SCT and App2Container docs/07

Swap a self-managed database or app server for a managed AWS equivalent without changing the surrounding architecture.

  1. Run an SCT assessment for schema/code compatibility before committing a wave date.
  2. Provision the target (RDS/Aurora, right-sized, Multi-AZ, encrypted) or run App2Container to containerize the app server.
  3. DMS full load, then CDC to keep the target in sync while the source stays live.
  4. Validate with DMS data checks (row counts, checksums) plus app-level smoke tests.
  5. Cut over: brief write-freeze, re-point connection strings, verify zero replication lag.
  6. Bake, then decommission the source.
Repurchase — move to SaaS docs/08

Replace the application with a SaaS product — the biggest risk here is adoption, not technology.

  1. Map legacy data fields to the SaaS data model; resolve gaps before migration, not during cutover.
  2. Design integrations via AWS AppFlow or direct API for every upstream/downstream dependency.
  3. Federate SSO from IAM Identity Center to the SaaS platform.
  4. Migrate historical data, reconcile record counts.
  5. Run a parallel period, then cut over and freeze the legacy system.
  6. Train users and brief the help desk before, not after, cutover.
Refactor — re-architect for cloud-native docs/09

Strangler-fig the monolith apart one bounded context at a time — never a big-bang rewrite.

  1. Identify bounded contexts (domain-driven design) as candidate services.
  2. Put a routing facade in front of the monolith; 100% of traffic still goes through initially.
  3. Extract one capability at a time onto its own compute (Lambda/ECS) and its own datastore.
  4. Backfill or CDC the relevant data, then shift the facade's routing rule.
  5. Decouple new services with EventBridge/SQS/SNS in place of direct calls.
  6. Repeat until the monolith is empty or intentionally reduced in scope.
Retire & Retain docs/10

Retire is a process with a paper trail; Retain is a decision with an expiry date — neither should happen silently.

  1. Retire: verify zero usage (data + business sign-off), give a formal objection window, archive data, disconnect integrations, then decommission and cancel licenses.
  2. Retain: log the reason, the owner, and a revisit trigger — a retain without a trigger date is scope creep.
  3. If a retained system must reach migrated workloads, connect it narrowly via Direct Connect/VPN into the specific VPCs it needs, or consider AWS Outposts if it needs native AWS APIs on-prem.
